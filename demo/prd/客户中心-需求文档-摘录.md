## 1. 需求背景

客户信息散落在业务中台与客户系统两个系统内：客户基础信息在业务中台，线索、跟进、拜访等分析信息在客户系统。用户无法在单一系统完成客户数据查询，信息孤岛导致无法形成完整客户画像。

- 信息集中：客户完整信息在一个页面查全，不再跨系统拼凑
- 数据可用：支撑流失预警、upsell 等反哺业务的场景
- 效率提升：客户信息查询效率提升

一期范围：业务中台现有客户数据增删改查操作迁移至客户系统。

## 2.1 创建客户

### 2.1.1 主流程

客户列表页 → 点击「创建客户」→ 客户状态查询弹窗 → 输入客户名称查询 → 无重复 → 打开创建表单 → 填写并提交 → 二次确认 → 创建成功 → 返回列表并置顶展示。

### 2.1.2 详细步骤

| 步骤 | 操作 | 系统行为 |
|---|---|---|
| 1 | 点击「创建客户」 | 弹出「客户状态查询」弹窗，标题为「客户状态查询（创建客户前请先查询是否已在系统）」 |
| 2 | 输入客户名称并查询 | 全局模糊匹配；未命中展示「暂无此客户，立即创建客户」 |
| 3 | 点击创建客户 | 打开创建表单浮层，填写过程自动保存到本地缓存 |
| 4 | 点击提交 | 前端校验必填与格式 → 二次确认「确定创建客户?」 |
| 5 | 确认 | 生成客户编号、记录创建人与创建时间、写入跟进人关系、sync_status=0 待同步；Toast「创建成功」 |

### 2.1.3 逆向流程

- 取消创建：提示「确定放弃编辑?」，确定后关闭且不保存；取消则返回继续编辑
- 中途退出：浏览器标签页关闭后，下次打开自动恢复缓存内容；叉掉浮层时提示「是否需要恢复上次版本」
- 不查询直接创建：不输入任何内容时不显示创建按钮，无法直接进入创建

### 2.1.7 异常处理

| 异常类型 | 触发条件 | 用户感知 | 系统行为 |
|---|---|---|---|
| 网络异常 | 请求失败 | Toast「网络异常，请重试」 | 保留输入 |
| 接口超时 | 响应超过 10s | Toast「请求超时，请重试」 | 保留输入 |
| 服务端错误 | 返回 500 | Toast「系统异常，请稍后重试」 | 记录错误日志 |
| 并发冲突 | 同名客户已被创建 | Toast「客户已存在」 | 阻止提交 |
| 同步失败 | 业务中台写入失败 | 用户无感知 | 后台异步重试，记录日志 |
| 会话过期 | token 失效 | 弹窗「登录已过期，请重新登录」 | 跳转登录页，登录后返回列表，缓存保留 |

## 2.2 客户合作状态查询

### 2.2.3 详细步骤

输入客户名称（支持全称、简称、别名）→ 查询 → 按名称模糊匹配全局客户 → 展示相似列表，含五条业务线合作状态与责任BD → 操作栏「跟进」发起跟进申请；若本人及下级为责任BD/责任CM，操作栏显示「查看详情」。

### 2.2.4 列表字段

客户名称、MTC / PAC / VASC-DMC / VASC-CMC / VASC-ECP 合作状态与责任BD（无则显示「-」）、操作栏。

### 2.2.5 合作状态枚举

| 状态 | 判定条件 | 颜色 |
|---|---|---|
| 合作中 | 近 90 天有消耗 | 绿色 |
| 沉寂半年内 | 近 180 天有消耗，但超 90 天无消耗 | 黄色 |
| 沉寂大于半年 | 超 180 天无消耗 | 红色 |
| 未合作 | 从未产生消耗 | 灰色 |

### 2.2.6 业务规则

| 编号 | 规则描述 | 处理方式 |
|---|---|---|
| BR-201 | 全局查询 | 不受数据权限限制，用于防撞单 |
| BR-202 | 模糊匹配 | 按客户名称、客户别名包含匹配，返回全部命中 |
| BR-203 | 业务线独立 | 五条业务线状态各自展示，互不覆盖 |
| BR-204 | 状态只读 | 由业务中台计算，客户系统只读展示 |
| BR-205 | 空查询 | 提示「请输入客户名称」，不发起请求 |

### 2.2.7 异常处理

- 无匹配：空状态「暂无此客户，立即创建客户」，创建按钮可用
- 结果过多：提示「结果较多，请输入更完整的名称」
- 网络异常：Toast「网络异常，请重试」
- 查询超时：超过 5s 提示「查询超时，请重试」

### 2.4.3 跟进审批

审批建议提醒文本规则：

1. 合作中 → 建议驳回
2. 沉寂半年内 / 沉寂大于半年 / 未合作：

   - 有责任BD且近 60 天有拜访或提单 → 建议驳回
   - 无责任BD且近 60 天无拜访无提单 → 建议通过

输出模板：当前业务的合作状态为：，责任BD为：，近60天提单/拜访情况为：，审批建议：通过 / 驳回

## 2.6 客户合并 / 存档

### 2.6.1 客户合并

合并仅改变客户及下游实体的当前归属和聚合展示关系，不物理删除旧客户和历史业务数据。

| 实体 | 合并后的处理方式 | 去重 / 冲突规则 |
|---|---|---|
| 客户 | 新客户保留；旧客户改为已存档并记录去向；旧客户信息不覆盖新客户 | 禁止旧客户与新客户相同；禁止循环合并 |
| 客户别名 | 旧客户名称、别名并入新客户别名集合 | 按标准化名称去重，忽略首尾空格、全半角、大小写；新客户名称不被覆盖 |
| 公司主体 | 主体不复制不删除，旧客户的有效关联增加到新客户 | 以主体编号判重，同一主体只保留一个有效关联 |
| 报价单 | 归属改为新客户，已删除的报价单不改 | 保留原客户、流程版本与合并批次 |
| 广告主 | 不同广告主均保留，统一在新客户下展示 | 按投放平台广告主 ID 判重，相同 ID 仅迁移关联 |
| Offer | 不单独迁移，随所属广告主聚合展示 | Offer 编号全局唯一；活跃、待确认的 Offer 禁止更换广告主 |
| 合同 | 草稿合同可调整归属；审批中、已签署、履行中、已终止合同不改正文与签署客户，仅聚合展示 | 合同编号唯一，不重复关联 |
| 补充协议 | 随原合同聚合展示 | 协议编号唯一，禁止脱离原合同迁移 |
| 授信额度及欠款 | 不直接相加，取授信较高的保留 | 合并审批未完成前不得释放来源客户额度 |
| 线索 | 旧客户已关联线索迁移为关联新客户 | 同一线索已关联新客户时不重复新增 |
| 跟进人 | 按「用户 + 业务类型」合并到新客户，重复关系保留一条有效记录 | 同一业务类型存在多个责任BD 时按新客户覆盖 |
| 拜访记录 | 不复制不改写，新客户详情通过合并关系聚合展示 | 以拜访记录 ID 判重；旧客户不再允许新增拜访 |
| 跟进申请单 / 审批单 | 历史工单保留原客户；审批中工单暂停并提示用户 | 不允许静默迁移，需选择撤回或改新客户重新提交 |

版本与审计：每次合并生成不可重复的 merge_id，记录 source_customer_id（可为多个）、target_customer_id、before_owner / after_owner、operator / approved_by、started_at / completed_at、status（合并审批中 / 成功 / 失败 / 已拆分）。

连续合并（A → B，之后 B → C）：A、B 均指向最终目标 C，保留完整链路，不覆盖中间批次。

### 2.6.1.1 边界场景

| 边界场景 | 处理规则 |
|---|---|
| 多个来源客户合并到一个目标 | 按一个 merge_id 执行；任一来源预检失败则整体不进入执行 |
| 旧客户已被合并 | 禁止再次作为旧客户提交，提示其最终新客户 |
| 新客户之后再次被合并 | 允许作为新的旧客户合并，系统维护完整合并链 |
| 循环合并 | 新客户历史链中已包含任一旧客户时阻止提交 |
| 双方存在同一公司主体 | 仅保留一个有效关联，主体与历史签约关系不变 |
| 报价单 / 合同正在审批 | 标记冲突项，审批中单据不自动改写 |
| 已签署合同客户名称不同 | 正文不修改，聚合展示并标注「签署客户：原客户名称」 |
| 不同币种、授信或欠款冲突 | 禁止自动合并额度，保留额度较高者，旧客户记录保留 |

### 2.6.1.2 合并审批字段

| 字段 | 必选 | 控件 | 说明 |
|---|---|---|---|
| 旧客户名称 | 是 | 搜索选择器 | 被合并方，合并后状态改为已存档，名称写入保留方别名 |
| 新客户名称 | 是 | 搜索选择器 | 保留方 |
| 选择取值 | 是 | 单选 | 取旧客户值 / 取新客户值，默认取新客户值 |
| 客户信用等级 | 是 | 下拉 | 默认未评级；枚举 未评级/E级/D级/C级/B级/A级/S级 |
| 客户类型 | 是 | 下拉 | 直客 / 代理，默认取新客户值 |
| 所属行业 | 是 | 下拉 | 默认取新客户值 |
| 行业（自定义） | 否 | 文本 | — |
| 客户别名 / 授信额度 / 不同业务线责任BD / 跟进人 / 历史跟进人 / 公司主体名称 / 投放平台广告主ID | 否 | 只读 | 选定客户后自动带出，辅助判断 |

### 2.6.2 业务规则

| 编号 | 规则描述 | 处理方式 |
|---|---|---|
| BR-601 | 旧客户名称自动并入保留客户别名 | 追加旧客户 name 至新客户 alias |
| BR-602 | 旧客户与新客户不可为同一客户 | 提示「旧客户与新客户不能相同」，阻止提交 |
| BR-603 | 新客户不可为已归档客户 | 提示「该客户已归档，请选择正常状态的客户作为保留方」 |
| BR-604 | 双方客户均必选 | 提示「请选择旧客户」/「请选择新客户」 |
| BR-605 | 必填字段校验 | 客户类型、客户级别类型、客户信用等级、所属行业为空则标红阻止 |
| BR-606 | 默认取新客户值 | 字段区全部自动带入新客户数据 |
| BR-607 | 切换开关整组联动 | 字段区整组刷新为另一方客户的值，手动调整值被覆盖 |
| BR-608 | 重置恢复初始态 | 清空双方客户选择与所有字段 |
| BR-609 | 合并操作留痕 | 记录操作人、操作时间、新旧客户名称、取值、客户信用评级 |

### 2.6.4 客户存档触发方式

- 触发条件：客户合并成功
- 归档原因：自动填充「已合并至 {新客户名称}」
- 归档人：合并操作人
- 归档时间：合并操作时间

### 2.6.5 存档后的数据处理

- 被存档客户详情数据完整保留，仅把客户名称合并至合并后保留客户的别名字段
- 列表选择「已存档」时，展示合并前的全部客户列表数据

## 4. 非功能性需求

### 4.1.1 响应时间

| 操作类型 | 目标响应时间 | 备注 |
|---|---|---|
| 客户列表查询 | ≤ 2s | 单页 50 条，含分页 |
| 客户详情页加载 | ≤ 2s | 含关联线索、跟进人、拜访记录 |
| 客户状态查询（前置查重） | ≤ 2s | 模糊匹配全局客户，返回前 20 条相似结果 |
| 客户创建 | ≤ 2s | 含客户编号生成、跟进关系写入 |
| 客户编辑保存 | ≤ 2s | 含变更日志记录、同步状态重置 |
| 跟进申请提交 | ≤ 1s | 含申请单号生成、通知推送 |
| 客户合并操作 | ≤ 3s | 含旧客户归档、别名合并、跟进关系迁移 |

### 4.1.2 批量操作

| 操作 | 批量上限 | 性能要求 |
|---|---|---|
| 客户列表导出 | 单次 10000 条 | ≤ 30s |

### 4.2 数据质量要求

| 数据项 | 准确性要求 | 校验规则 |
|---|---|---|
| 客户编号 | 100% 唯一 | 系统生成，生成后永久锁定 |
