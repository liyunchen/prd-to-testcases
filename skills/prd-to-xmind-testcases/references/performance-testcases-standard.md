# 性能测试用例规范

加载条件：用户明确要求「按性能测试」，**或 PRD 中出现 SLA、响应时间、QPS/TPS、并发数、数据量级、超时阈值、导出条数上限**。后者常被忽略——需求文档第 4 章常自带指标，不能因为用户没提性能测试就整章跳过。

## 一、必覆盖维度

### 1.1 指标与基线

- **响应时间**：文档给了 RT 就写进用例（P95 / P99 / 平均），标明被测场景、目标值、压测时长。
- **吞吐量**：有 QPS/TPS 或并发用户数的，写明目标值、持续时间、允许的错误率。
- **容量**：有单机/集群承载、连接数、内存约束的，写明约束与预期负载。

### 1.2 场景类型

| 类型 | 目的 |
|------|------|
| 基准 | 低负载下验证可用，作为后续对比基线 |
| 稳态 | 文档给定的正常/峰值负载下持续运行，验证 RT、成功率、错误率 |
| 峰值/尖峰 | 短时流量突增，验证不崩溃、降级生效、恢复时间可控 |
| 长稳 | 7×24 或长时间运行，观察内存泄漏、连接泄漏、RT 漂移 |

### 1.3 瓶颈与退化

- 阶梯加压逐步提升并发，观察 CPU、内存、I/O、依赖服务、数据库连接。
- 触发降级/限流/熔断的边界负载，验证返回约定错误码而非雪崩。

## 二、节点写法

- 标题：`场景类型 + 目标指标`，例如 `状态-客户列表 50 条分页 P95≤2s`。
- `- 前置：` 压测环境规格、机器数量、依赖版本、测试数据量级（多少客户、多少跟进记录、热点数据比例）。
- `- 步骤：` 并发数、QPS、持续时间、是否阶梯、混合场景各接口比例。
- `- 预期：` 明确的通过标准，如 `P95 ≤ 2s、成功率 ≥ 99.9%、无 OOM`。

## 三、指标缺失时

文档只写「响应快」这类定性描述时，不要编造数字。用占位写法：「目标 RT 以产品/运维约定为准」，并在「待确认问题」分支登记，请对方补具体指标后再执行。

## 四、常见误区

- 只抄了文档里的数字，没设计负载模型（并发多少、跑多久、数据多大）——数字无法执行。
- 只测单接口，不测混合场景——真实流量是混合的。
- 不写测试数据量级——同一接口 1 万数据和 1000 万数据差两个数量级。
