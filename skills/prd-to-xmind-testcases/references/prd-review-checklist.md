# PRD 歧义排查清单

写用例前先扫一遍 PRD，把问题收敛到 `## 待确认问题`。这一步比多写 50 条用例更有价值——用例再全，需求本身有洞也测不出正确的系统。

## 一、六类高频问题

### 1.1 同一事物多个叫法

同一字段或枚举在不同章节用不同名字。检查方法：把每个字段名在全文搜一遍，看是否有同义变体。

典型：「内部资源」vs「内容资源」、「客户级别」vs「客户级别类型」、「已归档」vs「已存档」。

### 1.2 规则与表单不对应

业务规则要求校验某字段，但表单里没有这个字段；或表单有字段，规则没定义校验。

检查方法：把规则表里的校验项与表单字段表逐条对撞。

### 1.3 数量/分页/排序描述自相矛盾

同一场景同时说「分页展示」和「只返回前 20 条」；或排序规则在列表页和详情页不一致。

### 1.4 可编辑性与必填性冲突

字段在 A 场景是只读，在 B 场景要求必填；或系统生成字段又被要求用户填写。

### 1.5 指标口径缺失

给了性能指标但没给测试条件（多少数据量、多少并发、P95 还是平均）；或给了上限但没说超限怎么处理（截断、报错、排队）。

### 1.6 边界场景只写了一半

写了「多来源合并到一个目标」，没写「合并过程中某个来源失败怎么办」；写了「并发编辑」，没写覆盖策略。

## 二、登记格式

每条问题写四段，缺一不可：

```
#### 待确认-客户来源枚举名称不一致
- 步骤：2.1.4 写作「内部资源」，2.3.3 写作「内容资源」
- 预期：确认为同一枚举并统一命名，或确认为两个不同取值
- 备注：影响「创建客户-客户来源枚举完整性」「客户编辑-来源切换」2 条用例
```

## 三、不要做的事

- 不要自己拍板选一个解释然后继续写用例——需求方的口径只有需求方能定。
- 不要把疑问写成注释埋在用例里——散在 200 条用例里没人看得见。
- 不要因为有问题就停下来不写——按最合理的假设先写，同时登记问题，交付时一并提出。
