# 通用测试用例设计规范

未指定接口测试或性能测试时的默认规范。按模块拆完后，每个子功能都要用下列策略过一遍，不得只写正常流程。

## 一、六种必用策略

### 1.1 正向（正常路径）

每个核心功能点至少 1 条。预期要写清「成功」的判定标准：界面变化、状态值、关键数据。

### 1.2 反向（非法与越权）

针对每个可校验的输入或条件，至少一类无效情况：格式错误、必填缺失、越权、重复提交、非法状态操作。

权限类需求必须成对覆盖：**有权限能用** + **无权限被拦**。只写前者等于没测权限。

### 1.3 边界值

从文档中提取所有「有范围 / 有长度 / 有数量 / 有时间窗口」的约束，每个约束取三类值：边界内有效、边界值、边界外无效。

典型：分页条数上限、模板数量上限、导出条数上限、字符长度上限、天数窗口临界（如「近 60 天」的第 60/61 天）、超时阈值。

### 1.4 等价类

有效等价类取 1~2 个代表值；无效等价类按违规类型各取一个代表值（格式、范围、必填缺失）。与边界值合并使用。

### 1.5 场景法

串起多个模块的端到端路径，落到 `## 端到端业务场景`。归纳 3~5 个典型用户目标（新客户接入、防撞单、数据合并治理、异常恢复），每个目标至少一条主流程 + 一条常见分支。

### 1.6 状态与流程

文档里有状态机、多步骤审批、角色切换时必须做：

- 列出全部状态与合法迁移，逐条正向覆盖；
- 覆盖非法跳转（跳过审批、终态再操作、驳回后重审）；
- 覆盖中间态被打断（审批中客户被合并、审批中单据被修改）。

## 二、优先级判定

每条用例必须标 `[P0]` / `[P1]` / `[P2]`，逐条判定，禁止整批默认 P1。判定时按下列顺序问，命中即定级：

### P0 —— 阻塞发布

命中任意一条即 P0：

- 主流程走不通（创建、提交、审批、合并执行不了）
- 资金、额度、欠款、授信算错或多算
- 越权可访问、可编辑、可操作（权限失效）
- 数据写错、写重、丢失（唯一性失效、并发覆盖、归档丢数据）
- 状态机断链（该流转的没流转、终态还能操作）
- 审计与追溯缺失（合并批次、变更日志、操作留痕）

### P1 —— 影响可用

- 异常提示缺失或错误（网络异常、超时、服务端错误）
- 边界校验失效（超长、超限、临界值处理错）
- 次要字段联动错（国家↔城市、来源↔子字段）
- 排序、筛选、分页、模板等辅助功能不可用
- 通知、消息、同步状态类
- 性能指标不达标

### P2 —— 体验瑕疵

- 文案、提示语、占位符
- 空状态、加载态、置灰态
- 二次跳转、双击进详情
- 历史记录、辅助信息的展示

### 比例参考

正常系统的分布大致是 **P0 20%~35%、P1 45%~60%、P2 10%~20%**。若 P0 低于 10%，说明核心链路没识别出来；若 P0 高于 45%，说明判定过宽，失去了优先级的意义。

## 三、字段级覆盖原则

PRD 字段表是最容易漏的部分。按以下规则处理，避免要么全展开到 500 条、要么全漏：

| 字段类型 | 覆盖要求 |
|----------|----------|
| 必填字段 | 全表单合并为 1 条「必填缺失」用例 + 逐个字段抽查关键项 |
| 枚举字段 | 每个枚举字段 1 条「枚举完整性」用例，列出全部取值 |
| 有长度/范围 | 每个字段 1 条边界用例，至少覆盖上限与超限 |
| 只读/系统生成 | 合并为 1 条「不可编辑」用例，列出全部只读字段 |
| 联动字段 | 每个联动关系 1 条（如国家↔城市必填、类型↔子字段显示） |
| 多值/列表字段 | 1 条多值展示用例 + 1 条去重/排序用例 |

字段总数超过 50 个时，在模块末尾加一条「字段完整性巡检」用例，把未单独展开的字段列在备注里，明确标注为「已合并覆盖」。

## 四、数据一致性

凡涉及双系统同步（如上游业务系统↔下游客户系统）、异步任务、缓存的，必须覆盖：

- 同步成功后的最终一致；
- 同步失败时的用户感知与后台重试；
- 并发编辑的覆盖顺序；
- 归档/删除后数据不丢失、不产生孤儿数据。

## 五、产出前的自检清单

写完必须逐条过一遍，任何一条不过就回去补：

1. 每个 PRD 章节都有对应 L1 模块？没有的话，是漏了还是有意合并？
2. 文档里每个业务规则编号（BR-xxx）都至少被一条用例引用？
3. 每个状态机的每条迁移都有 `状态-` 用例？非法跳转有覆盖？
4. 每个权限点都有「有权限」和「无权限」两条？
5. 每个数量/长度/时间窗口约束都有边界用例？
6. 有端到端场景分支吗？至少 3 条？
7. 文档里的矛盾、缺失、口径不清，都进「待确认问题」了吗？
8. 每条用例的预期都是可判定的吗？有没有「显示正常」「功能可用」这种废话？
9. 前置条件写了吗？换个人拿这份用例能独立执行吗？
10. 每条用例都标了 `[P0]/[P1]/[P2]` 吗？P0 占比是否落在 20%~35%？

## 六、常见退化信号

出现以下情况说明产出质量在下降，需要回头补：

- 正向用例占比超过 75%（说明异常和边界没做够）；
- 一条用例里塞了 3 个以上互不相关的验证点；
- 预期里出现「正确」「正常」「符合预期」而无具体值；
- 所有模块用例数量高度平均（真实系统一定有主次）；
- 通篇没有一条用例需要特定测试数据（说明没考虑前置条件）；
- 优先级几乎全是 P1，或 P0 超过一半（说明没逐条判定，只是整批填了个默认值）。
