# 测试用例大纲结构规范（唯一层级定义）

本文件是层级的**唯一权威**。其他文件不得再定义另一套层级，避免出现两套互相矛盾的模型。

## 一、五层结构

| 层级 | Markdown | XMind 节点 | 含义 |
|------|----------|------------|------|
| L0 | `# 标题` | 中心主题 | 项目/产品名 + 测试用例 |
| L1 | `## 标题` | 一级分支 | 功能模块，与 PRD 章节一一对应 |
| L2 | `### 标题` | 二级分支 | 子功能 / 场景组 |
| L3 | `#### 标题` | 三级分支 | 单条测试用例（标题即用例名） |
| L4 | `- 文本` | 叶子节点 | 前置 / 步骤 / 预期 |

硬性规则：

1. 全文只能有一个 `#`，XMind 只认第一个作为中心主题。
2. `#` 与标题之间必须有一个空格。
3. `-` 条目**只能**出现在 `####` 之下。挂在 `###` 或 `##` 下会导致 XMind 里步骤变成用例的兄弟节点。
4. 禁止用 `1.` `2.` 有序列表表达层级，XMind 不映射。
5. 层级不得跳级（`##` 下直接出现 `####`）。
6. 文件保存为 UTF-8，不带 BOM。

## 二、L3 用例标题写法

格式：`类型-场景描述 [优先级]`

- **类型前缀**（必填，五选一）：
  - `正向-` 合法前置下的正常路径
  - `反向-` 非法输入、越权、违反约束
  - `边界-` 临界值、上下限、空值、超长
  - `场景-` 跨模块端到端串联
  - `状态-` 状态机迁移与非法跳转
- **优先级**（**必填**，`[P0]` / `[P1]` / `[P2]` 三选一）：
  - `[P0]` 阻塞发布：主流程走不通、资金/额度算错、越权可访问、数据写错或重复、状态机断链
  - `[P1]` 影响可用：异常提示、边界校验、次要字段联动、排序筛选、通知
  - `[P2]` 体验瑕疵：文案、空状态、占位符、二次跳转、历史记录展示
  - 判定口径见 `testcase-design-standard.md` 第二节，必须逐条判定，不允许整批默认 P1
- 描述要能独立看懂，例如「正向-创建客户时客户名称重复被拦截 [P0]」，不要写「测试点 1」。

## 三、L4 条目写法

| 条目 | 是否必填 | 说明 |
|------|----------|------|
| `- 前置：` | 可选 | 执行前必须满足的数据、角色、状态。合并类、审批类用例**强烈建议**写 |
| `- 步骤：` | 必填 | 一条用例一段操作路径，动作用「→」串联 |
| `- 预期：` | 必填 | 可判定的结果：界面变化、状态值、提示文案、落库结果 |
| `- 备注：` | 可选 | 依赖环境、待确认口径、自动化建议 |

预期必须是**可判定**的。写「显示正常」不合格，要写「Toast 提示『旧客户与新客户不能相同』且不发起请求」。

## 四、两个特殊 L1 分支

### 端到端业务场景

场景法必须落在独立分支里，否则会被模块切碎而漏掉。固定命名 `## 端到端业务场景`，其下 `###` 按用户目标分组（如「新客户全链路」「客户合并全链路」），`####` 用 `场景-` 前缀。

跨 3 个以上模块、串起 4 个以上动作的，才放这里；否则留在原模块。

### 待确认问题

PRD 中的矛盾、缺失、口径不清，固定收敛到 `## 待确认问题`，每条写清「原文位置 + 冲突点 + 影响哪些用例」。不要让歧义散落在用例里靠人记。

## 五、模块拆分原则

- 以 PRD 章节为第一依据，命名与文档用语一致，便于追溯。
- 一章内容过长（超过 60 条用例）时，按「对象」或「操作类型」拆成多个 L1，不要靠加深层级解决。
- PRD 没有章节结构的，按「用户可感知的功能块」划分。
- 非功能性需求（性能、数据质量、兼容性）单独成 L1，不要塞进功能模块。
